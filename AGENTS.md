# AGENTS Overview

Этот документ описывает архитектуру и политику работы «агентов» в проекте LLMSecurity Lab с отсылкой к рекомендациям OpenAI по безопасным ассистентам и сопутствующей документации.

## 1. Картина мира
- **Назначение**: исследование устойчивости LLM к prompt-инъекциям и демонстрация многоуровневых защит.
- **Типы агентов**:
  - **Test Runner Agent** – выполняет сценарии атак, взаимодействует с моделью и запускает защитные слои.
  - **Defense Pipeline Agent** – конвейер слоёв L1–L9, обрабатывающий запрос до и после обращения к модели.
  - **Model Client Agents** – адаптеры к конкретным моделям (примеры: `DummyModelClient`, `OpenRouterModelClient`).
  - **UI Agent** – PyQt-интерфейс, который управляет прогоном тестов и визуализацией результатов.

## 2. Соответствие рекомендациям OpenAI
Рекомендации OpenAI по созданию безопасных ассистентов (OpenAI Policies, Safety Spec):
- **Примат системных инструкций** – реализован через Policy Engine (слой L4), который гарантирует неукоснительное следование правилам.
- **Контроль инструментов** – Gatekeeper (L5) требует явного разрешения перед выполнением потенциально опасных действий от имени агента.
- **Контентная модерация** – Output Guard (L7) блокирует токсичный и запрещённый контент на выходе.
- **Разделение данных и инструкций** – Context Firewall (L3) маркирует контент `DATA_ONLY`, чтобы исключить «инструкции» из RAG-источников.
- **Логирование и аудит** – Test Runner собирает `layer_logs` и `defense_decision`, что облегчает аудит и расследование инцидентов.
- **Rate limiting** – Rate/Scope Guard (L9) ограничивает частоту вызовов и размеры входных данных, предотвращая злоупотребления.
- **Человеческий контроль** – `Decision.ESCALATE` инициирует ручную проверку в случаях сомнений (соответствует идее human-in-the-loop).

## 3. Роли и ответственность
| Агент | Роль | Ключевые контракты | Поведение при сбоях |
|-------|------|--------------------|---------------------|
| Test Runner | orchestration | `TestSuiteService`, `TestRunner` | Останавливает тест и логирует ошибку, отдает статус FAIL |
| Defense Pipeline | безопасность | `IDefenseLayer`, `DefensePipeline` | Возвращает `BLOCK`/`REWRITE`/`ESCALATE` с причинами |
| Model Client | интеграция | `ModelClient` | Пробрасывает исключения сети, чтобы Test Runner мог зафиксировать ошибку |
| UI Agent | оператор | `UISuiteController` | Показывает ошибки пользователю и предлагает повторный запуск |

## 4. Жизненный цикл взаимодействия
1. UI/CLI формирует `PromptBundle`.
2. Defense Pipeline обрабатывает ввод (`before_send`).
3. Model Client отправляет запрос в модель (или имитатор).
4. Defense Pipeline анализирует ответ (`after_recv`).
5. Output Evaluator фиксирует Pass/Fail.
6. Результаты логируются и попадают в отчеты.

## 5. Конфигурация и управление
- **Профили защиты** (`config/profiles.yaml`) – включают слои и их параметры.
- **Политики** (`config/policy.yaml`) – правила для Policy Engine (запрет раскрытия системного промпта, запрет смены роли и т.п.).
- **Тестовые сценарии** (`data/prompt_tests.yaml`) – определяют входные сообщения и критерии Pass/Fail.
- **API-ключи** – Model Client (например, OpenRouter) считывает ключ из переменных окружения. Хранение в SCM запрещено.

## 6. Риски и смягчающие меры
- **Утечка системных инструкций** → L4 блокирует, L7 модерация, журналы фиксируют попытки.
- **Эскалация привилегий через инструменты** → L5 требует токенов, L9 контролирует частоту.
- **Adversarial suffix / obfuscation** → L6 и L1 нормализуют и удаляют подозрительные хвосты.
- **Indirect prompt injection через RAG** → L3 очищает HTML и скрытые элементы.
- **Ложные срабатывания защит** → A/B режим фиксирует `false_positive`, что позволяет оператору калибровать пороги.

## 7. Стратегия расширения
- Подключение реальных guard-моделей (например, OpenAI Moderation, Llama Guard 2).
- Интеграция с OpenAI Evaluate API для сравнения ответов.
- Встраивание человеческого аппрува через очередь задач.
- Настройка централизованного журнала (SIEM) на основе `JSON`-отчетов.

## 8. Операционные рекомендации
- **Мониторинг**: отслеживать Pass%, вклад слоев, FP-rate.
- **Обновления профилей**: периодически обновлять YAML-файлы с учетом новых векторов атак.
- **Безопасность API**: использовать секретные хранилища, шифровать ключи, вращать токены.
- **Тестирование**: перед релизом прогонять базовый и защищенный режимы, сравнивая разницу.

## 9. Glossary
- **Prompt Injection** – атака, заставляющая модель нарушить инструкции.
- **Defense-in-depth** – многоуровневый подход к защите (L1–L9).
- **A/B Run** – сравнение baseline (без защиты) и профиля защиты.
- **Escalation** – запрос ручной проверки, когда автоматическая оценка не гарантирует безопасность.
